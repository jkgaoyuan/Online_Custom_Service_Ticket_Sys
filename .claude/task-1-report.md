## Concerns
- **env.py modification**: Added `sla_record` and `notification` imports to `backend/alembic/env.py` so Alembic autogenerate could detect the new models. This was necessary because `env.py` imports model submodules directly rather than via the package `__init__`.
- **No running PostgreSQL locally**: Used a temporary Docker PostgreSQL container (`docker run postgres:15-alpine`) to run `alembic upgrade head` and `alembic revision --autogenerate`. The container was stopped and removed after use.
- **False positives in autogenerate**: The autogenerated migration incorrectly included dropping two unique constraints (`email_ingestions_message_id_key`, `uq_ticket_replies_email_message_id`). These were removed from the final migration because they are unrelated to this task and could damage existing data.
- **Partial index choice**: The brief required two partial indexes on `sla_records` and one on `notifications` but did not specify exact predicates. Chose:
  - `ix_sla_records_first_resp_active` on `first_resp_due` WHERE `first_resp_at IS NULL`
  - `ix_sla_records_resolution_active` on `resolution_due` WHERE `resolved_at IS NULL`
  - `ix_notifications_unread` on `(user_id, created_at)` WHERE `is_read = false`
  These are well-suited for the upcoming Celery scan tasks (Task 4).
- **Data migration values**: Flat `sla_config` values are copied as-is into all four priority buckets (P0-P3). If different values per priority are desired, a follow-up manual migration or admin UI update will be needed.
